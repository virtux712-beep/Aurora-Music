# Aurora Music 0.1.0 — 发布包说明

Electron + Vue 3 的桌面音乐播放器。本页是**发布包**（`release/aurora-0.1.0/`）的说明：装哪个、怎么装、这一版包含什么、验证到什么程度、哪些地方还有边界。

构建时间：2026-09-16 21:59（三种启动方式同批生成）。发布包由 `npm run release:pack` 组装，同内容可重跑出相同字节。

## 2. 怎么装

- **安装版**：运行 `installer\Aurora-Music-Setup-0.1.0-x64.exe`。非静默安装，可以选目录；开始菜单与桌面快捷方式由安装程序创建。
- **免安装版**：把 `portable\Aurora-Music-Portable-0.1.0-x64.exe` 放到任意位置双击。它会在用户目录下建自己的数据目录，不写注册表、不需要管理员权限。
- **系统要求**：Windows 10/11 x64。安装包内已含 Electron 34 运行时，无需另装 Node。

数据位置：`%APPDATA%\aurora-music\`（`aurora.db` 曲库索引、`settings.json`、`logs\crash.jsonl`、`covers\`、`lyrics\`）。卸载不删数据，需要时手动清理即可。

## 4. 源码包（`source/Aurora-Music-0.1.0-source.zip`）

源码**单独成包**，与程序包并列放在 `source/` 下（就是这样要求的：程序与源码各自一个包，不混在一起）。里面是**可直接重建**的完整源码，220 个文件，不含 `node_modules`、`out/`、`release/`、`tools/.build/` 等生成物：

```
src/                 主进程 / preload / 渲染层 / 共享类型（TypeScript + Vue 3 SFC）
tools/               验证脚本（smoke 套件与打包产物验收检查）
build/               图标与安装包资源
docs/                设计说明
package.json         依赖、脚本、electron-builder 配置
package-lock.json    锁定版本
tsconfig*.json  electron.vite.config.ts  eslint.config.js  README.md  .gitignore
```

重建：

```bash
npm ci                 # 按 lock 文件安装
npm run build          # 产出 release/win-unpacked + 安装包 + 免安装包
npm run release:pack   # 归位到发布包分类目录、重打源码包、重算校验和
npm run release:verify # 只核对现有文件与 SHA256SUMS.txt 是否一致
npm run verify         # 类型检查 + lint + 全部 smoke + 打包产物验收
```

源码包内**不含任何密钥或个人数据**：整个工程没有 `.env`，本地 API token 是运行时生成的，日志写入前会抹掉路径与 token 形状的字符串。打包脚本另外拒绝 `.env*`、`*.log`、`secrets.json`、`*.pfx`、`*.p12`、`.DS_Store`——即使这些东西被放进工作树也进不了包。

打包脚本（`tools/make-release.mjs`）里有两个刻意的选择，都是手工打包踩过坑才加的：

- **条目名一律用 `/`**。手工用文件遍历打的包会把 `src\main\index.ts` 原样写进 zip，在 Linux/macOS 上解出来是**一个名字带反斜杠的文件**，而不是目录树。现在条目名由脚本按 `/` 拼写，打完包再回读归档字节断言「反斜杠条目 = 0、含路径条目 ≥ 90%」，并把「目录树是否真的存在」做成断言而不是靠眼睛看。
- **同一份内容打出相同字节**。所有条目的时间戳被钉死（1980-01-01，可用 `SOURCE_DATE_EPOCH` 覆盖）；若每次钉打包时刻，哈希就会变，`SHA256SUMS.txt` 也就什么都证明不了。已实测：连打两次哈希一致。

### 帧率可以自己填，平台访问有了安全模式，音源能绕开协议自己装一个

**帧率不再是六个写死的档位。** 「跟随系统 / 30 / 60 / 90 / 120 / 144」之外多了一个数值入口（24–240，与设置页里那句提示同源），输入的值会走完整条链：设置持久化（渲染层 localStorage 里的 `aurora:frame-rate`）→ 读回时按同一个契约解析 → 帧治理器的预算（`1000 / fps`，且不超过屏幕刷新率）→ 设置页按钮上显示当前值。顺手修掉一个真 bug：**数值档位原先重启后会丢**——存储里是字符串，而校验器只接受数字，于是每次读回都被当成非法值退回「跟随系统」，界面显示 60 而实际按屏幕刷新率画。现在解析器与契约放在同一个模块（`parseFrameRateChoice`），往返由单元断言钉住，Lab 里显示的档位与真正生效的档位也由同一条断言对齐（不许面板自己说谎）。

**平台访问安全模式**是三个开关中的第三个，一次收紧三件事：① 未授权主机不再自动放行（上面那个「播放时自动允许」当场变成不可用，避免两个开关同时打开这种自相矛盾的状态）；② 拒绝明文 `http://` 的**接口**请求（音频字节不受影响，仍按主机白名单中继）；③ 之后新装/导入的音源默认禁用，要手动启用才会加载或联网。界面把代价写在开关旁边：只用 http 接口的音源会解析失败，报错里会写明是安全模式拒的。

**安装音源的第三条路：不经过任何脚本协议，直接新建一个自己的音源。** 入口在安装区（`data-new-custom-source`），打开的是声明式清单编辑器，不跑任何代码。它填的是同一个校验器的空白：以前「合法的清单」和「运行时真能工作的清单」之间有缝——校验只认 `https`，而聚合类接口大量用明文 `http`；省略 `permissions` 会被判不完整，而运行时本来就把省略当作 `network`；`file:` 这类端点则一直该拒。现在三处对齐，并且**清单能解析出东西**这件事是端到端验的，不是靠校验通过：URL 模板生成封面 → 经中继取到真字节；声明 `files` 列表时挑中 MP3 并组成中继地址 → 中继读到音频；列表里没有可播放文件时报 `NOT_FOUND`。

### 空闲时那张粒子画布的背板分辨率

上一版把暂停时的门闸从 60 fps 降到 30，这一版接着往下：暂停时（或窗口不在前台时）**画布背板按 0.7× 分辨率渲染再放大**。它画的是柔光粒子，放大后观感差别很小，而这是暂停态里单项最大的一笔（每帧重绘并重传一份整屏纹理）。当前分辨率由帧治理器发布成可读属性（和 `data-bg`、`data-fx-focus` 一样是读数而不是声明），Lab 里一并显示。

如实说：**这一项收益没能从机器噪声里分离出来**。归因表在改前后给出 0.055 → 0.064 核，而同一状态重复测量的回合间波动本身就有 ±0.1 核——也就是说这次改动省下的量小于本机噪声，我不能声称量到了它的收益，只能说机制成立（纹理上传量按平方下降）且没有把暂停态变重。

### 这一版修掉的四处（都指向同一句用户可见的失败：装了音源却连不上）

1. **未授权主机被报成“找不到”**。一个平台可能由多个音源解析，原来无论因为什么失败都报 `NOT_FOUND`，并把每个音源的错误拼成一段话——于是“尚未授权访问某主机，请在音源管理页允许”这句本来一键可解的提示，被埋在别的失败信息中间，错误码还说这曲子“不存在”，界面因此无法提供任何补救入口。现在“未授权”单独成一条 `PERMISSION`，提示直接给出主机与入口：`音源「X」需要访问 <主机>，尚未授权。请到「设置 → 音源管理」点「允许 <主机>」后重试。`
2. **中文域名（IDN）的授权永远匹配不上**。运行时比较的是 `new URL(url).host`（punycode 形式），而授权里存的是写下来的中文域名，二者不是一个字符串：界面上“已允许”，请求仍被拒。现在授权一律规范成 punycode，并且被拒主机的提示里显示的就是这个可授权形式。
3. **音源管理页的待授权列表是缓存的**。安装音源时打开过该页，播放被拒后再回来看到的还是打开那一刻的列表（通常还没有被拒的主机），于是“允许该主机”的按钮根本不出现——看起来像只能重装音源。现在每次进入该页都重新拉取。
4. **首次播放不再需要用户自己做任何事**。很多音源要到取播放地址时才知道要访问哪个主机（本机已装的 11 个里有 6 个是把主机名拼出来的），安装时的静态扫描无法预知，于是第一首歌的第一次请求被拒——在别的机器上这就是“装了音源却连不上”。现在：被拒 → 自动允许记下的那台主机 → 立刻重试。授权写在同一个位置（音源的允许列表，可撤销），并留下一条审计记录；想回到严格行为，在「设置 → 音源管理 → 播放时自动允许音源申请的主机」关掉即可，关掉后恢复为拒绝 + 卡片上一键允许。

边界说明（仍然成立的部分）：音源**永远无法自己给自己授权**——它不能调用这段逻辑，也不能指定想放行哪台主机；能被自动放行的只有“刚刚被拒绝的那一台”，而那条记录由拒绝本身产生。内置平台的允许列表依然写死在代码里，不受此开关影响。

### 整屏背景动画的冻结：一半被层叠顺序吃掉了

播放器里的装饰层分两半：画布那半（氛围粒子、频谱）每隔一帧都要问帧治理器「这一帧能画吗」，所以失焦会被降到 12 fps；**关键帧那半（整屏背景漂移、光晕呼吸）问不了任何人**，一个可见但失焦的窗口，合成器照样按显示器节奏每帧重画整张背景 —— 连带它上面所有玻璃面板的模糊。结果是同一条策略的两半在打架，最贵的那层反而是唯一没被管的。

本次把两半合成一条策略（新增 `data-fx-focus`，由帧治理器在 focus / blur / visibilitychange 时写），并在此过程中查出后一个真问题：**暂停时的冻结对五套主题从来没生效过**。原因是每套主题都用 `animation:` 简写声明自己的漂移，而简写会把 `animation-play-state` 重置回 `running`；那几条规则与冻结规则特异性相同（都是 0-3-0），谁在后面谁生效 —— 而简写在后面。默认配方因为声明写在 `base.css`（更早的文件）反而是好的，所以只测一套主题会以为它没问题。修法是把冻结规则移到样式表末尾，不靠 `!important`。

实测（打包产物、交错采样、同一状态下只切「冻结」开关，所以差值只属于关键帧这一层）：

```
关键帧在跑  0.460 核 · 0.446 核
关键帧冻结  0.276 核 · 0.307 核
→ 长期省 0.161 核，约 36% 相对
```

用「全应用处理器秒 / 墙钟秒」（累积计数）而不是瞬时百分比：上一轮已经发现同一状态的 GPU 百分比会因窗口遮挡在 0% 与 50% 之间摆。注意这是**窗口在前台**时量的，即这一层成本的上界；窗口已被系统节流时能再省的更少。

### 暂停时的功耗：找出最大的一项，并把它量下来

前一版把整屏 CSS 背景在暂停时冻住了，但**停下来的只有那个窗口**：暂停后的播放器仍然活跃，只是没人去问"剩下的钱花在哪"。这一版先问再改。

新加的 `tools/idle-cost-check.mjs` 做三件现有探针做不到的事，每件都是被一次错误的读数逼出来的：

- **按进程类型分摊**：`renderer` / `gpu-process` / `main` 从各自命令行里读，而不是看进程顺序。第一个读数就是三个视图**完全一样**（各 0.39 核），而 CDP 的 CPU profile 在 6 秒里只找到 **6 ms** 的 JavaScript —— 光看总数，下一步一定会改错地方。分摊后真相很清楚：GPU 进程 ~0.26 核，renderer ~0.12 核，也就是说钱花在合成上，不在脚本上。
- **逐层归因**：把候选层一个个屏蔽掉再量同一个状态（画布粒子层 / CSS 背景层 / 全部 `backdrop-filter`），每轮之前重测基线。
- **断言策略本身**：`data-fx-gate` 与 `data-fx-draw` 由帧循环自己写，所以"我没让静止画面跟高刷重绘"是读数而不是声明。

过程中两次读数本身是坏的，都记在代码注释里：暂停判定用 `document.querySelector('audio')` —— 而两个 deck 是 `new Audio()`，**从未挂进 DOM**，于是 `null !== true` 永远等于"正在播放"，第一版把暂停的机器量成了播放；而 Node 在 Windows 上把带内嵌双引号的参数传给 `CreateProcess` 时会破坏它，`-Filter "Name = 'Aurora Music.exe'"` 在 Node 里静默失败、在 shell 里手敲却完全正常，于是归因表整张是零。现在脚本里没有双引号也没有换行，采样拿不到数据时会自己喊出来。

暂停态逐层实测（打包产物，歌词页，交样采样取中位数）：

```
                    归因（改动前）        改动后
整机                0.39 核               0.26 核
其中 GPU 进程       1.65 核·秒 / 6 s      1.06 核·秒 / 6 s
画布粒子层省下       0.247 核 ≈ 总量 65%    0.133 核
CSS 背景层省下       0.000 核（已冻住）     0.039 核
全部 backdrop-filter 0.120 核（玻璃观感）    0.046 核
```

改动只有一个常量：`PAUSED_GATE_MS` 从 `1000/60` 改为 `1000/30`。暂停时最大的单项就是那张**全屏画布**（每帧重绘并重传一份 2880×1620 纹理），而它画的是每秒移动几像素的尘埃：30 fps 对这类慢速漂移无可察觉，却把这一项直接减半。歌词滚动、唱盘旋转都不走这个门闸，所以文字与唱片的运动不受影响；一拍开始播放，面板的原始帧率立即恢复（`check:idle --state playing` 专门盯这一点，不可达时明确报 SKIP 而不是报绿）。

`check:focus` 顺带修掉一条**假红**：原来断言"合成 focus 事件后属性必须回到 active"，但治理器发布的是 `focused && !document.hidden` —— 窗口被遮挡时 `background` 才是**正确**答案（"没人看"本来就包括这一种）。现在这两个值一起读，失败提示自带可见性状态。

### 每个音源一个独立管理页（互不影响）

音源列表页每张卡片上都有「管理」，进入 `#/settings/sources/<id>`：**自检与修复 / 联网授权 / 配置 / 能力与平台 / 错误历史** 五个分区，全部只作用于这一个音源。自检用真实操作一步步走（已安装 → 已注册 → 已启用 → 配置完整 → 搜索 → 取播放地址 → 联网授权），每步都给出结论、错误码与耗时；其中只有「被拒」这一种失败会被修——「自检并自动修复」会允许被拒的那台主机并重试一次，并把「自动允许 <主机> 后重试」写进那一步。其余失败（超时、无返回、配置不对）保持原样，不做假装成功的重试。

「互不影响」是在打包产物上验的，不是靠代码结构声称的：在详情页撤销一台主机后，列表与库里同时少这一台；点「自检并自动修复」后它被重新允许、重试记录出现在报告里；而这两次操作前后对比整张音源登记表，**只有这一个音源的授权列表发生变化**——其它音源的主机、状态、开关、权限一位没动，也没出现第二个被改动的字段。

### 全量自检：换了一台机器 / 换了一张网之后，谁还能用

音源管理页原来有一个「检查全部」，它问的是“连得上吗”并点一个点。这不够回答真正的问题：“换机器之后，谁要我动手？”所以单音源的「自检」（真的搜一次、真的取一次地址）现在能一次跑遍**所有已启用音源**，并把结论归成五类：

```
待授权  需要访问 <主机>，尚未授权          ← 行内直接一个「允许」按钮
超时    请求超时（12000ms）                ← 网络，不是音源坏了
待配置  需要填写参数才能工作
未加载  已启用，但运行时里没有它           ← 脚本加载失败，以前你根本看不见
出错    其余，带真实错误码
正常    搜索与取播放地址都正常
```

两类刻意分开：“答了但没有结果”（`empty`）与“正常”各占一类——一个关键词没命中的音源是健康的，把它归进故障里就会被人“修”到坏为止；“未加载”也单独一类，因为它在任何其他视图里都长得像“慢”。

几个决定写在了参数里：并发 2（十个音源能在一口气内跑完，又不会让慢网络同时背十个搜索——旧的「检查全部」也是逐个跑的），失败不停（整个功能的理由就是那一个坏掉的音源），以及**分类在主进程**。最后这一条是为了让这张表和它链到的详情页永远说同一句话：如果渲染层自己从步骤文本里重推分类，两处迟早不一致，而不一致比没有分类更糟。

实测（本地夹具，四种结论都是真的发生的：请求真的被拒、真的超时、真的答了空）：

```
全量自检: 每个已启用音源都有一行结论      {"checked":4,"rows":["smoke-source:ok","batch-empty:empty","batch-hang:timeout","batch-locked:unauthorized"]}
全量自检: 没返回的报超时并带 TIMEOUT 码    {"ms":24293,"verdict":"timeout","code":"TIMEOUT"}
全量自检: 未授权的行直接给出要放行的主机  {"pendingHosts":["127.0.0.1:60806"],"verdict":"unauthorized"}
全量自检: 汇总句把四类都说出来            4 个已启用音源：1 个正常 · 1 个正常但这个词没结果 · 1 个待授权 · 1 个超时
全量自检: 放行后同一音源立刻变正常        {"counts":{"ok":2,"unauthorized":0}}
```

打包产物上验的是另一件事：全新安装（一个音源都没有）时它必须**说“没有已启用的音源”**，而不是给一个空盒子——批量功能最容易在这里骗过测试。装上音源后再跑一次，行数要与应用自己报的“已启用”数量相等。

### 功能之间的接缝：四个“各自都对、放在一起就不对”的地方

这一轮不再加功能，而是把已经有的事对齐。四个都藏在接缝里，单看任何一处都看不出问题。

**① 报错里音源名说了两遍。** 权限层以音源名开头，沙箱宿主又把名字加回它拿到的消息，平台聚合再把名字加回去拼失败列表——每一层单独看都对，叠在一起就是用户看到的 `E2E 解析音源：E2E 解析音源：安全模式已开启…`。文字重复不会报错，它只会让那句**告诉你该去哪个开关**的话看起来像坏了，于是人不再读它。现在名字只加一次（`namePrefixed`，一处共享规则），单跑与端到端各有一条断言，后者读的是真实消息。

**② 安装结果里“被策略禁用”是界面自己猜的。** 安全模式会把**新装**音源设为禁用，而重新保存一个用户已经启用的音源时主进程故意不动它（编辑已经信任的东西不该被静默关掉）。页面拿的是自己那份安全模式开关，两种情况都会说“该音源默认禁用”——其中一种当场就是假的。现在这个布尔值只能由主进程给出（`disabledByPolicy`），界面原样转述；并且顺带修掉一个更早的错：在**只是检测到**文件、还没按下安装的时候，提示里就已经写着“已默认禁用”。

**③ 「自检并自动修复」在安全模式下仍然会偷偷授权。** 播放的两条路径会先问策略再修，而这个按钮直接调修复函数，于是开关在界面上写着“未授权主机不再自动放行”，行为却相反。现在修复入口自己先问策略，并把拒绝的原因带进自检报告（`repairBlocked`）——因为“没什么要修的”和“不允许我修”都是空列表，而后者需要你动手。

**④ 功能状态卡漏登记了刚做出来的东西。** 卡存在的唯一理由就是让人一眼看出“有什么、还差什么”，而安全模式、免脚本的自定义入口、帧率自定三条全不在上面。现在补上（共 51 条：50 已实现 + 1 缺口），并加了一条按名字钉住的断言——以后加了功能忘了登记，`check:features` 会当场红。

## 6. 已知边界（如实列出）

1. **迷你播放器窗口未实现**——功能状态卡里唯一标着"待实现"的一条。它不是加个窗口那么简单：小窗必须是"只显示、不播"的第二个渲染进程，否则会与主窗口抢播放，需要独立 preload、页面入口与主进程广播，属于要单独验证的一块。
2. **听觉验证**：自动化套件用 `--mute-audio` 运行以保持安静，"音乐确实在响"是靠分析器能量 + 播放时钟 + 输出端确连目的地三项读数证明的，不是靠录音比对。
3. **空闲开销**：暂停时背景光晕/漂移会冻住（实测 GPU 进程 44~50% → 19~21%），玻璃模糊半径同时收拢；播放时仍按用户在设置里选的帧率渲染（默认跟随显示器，165 Hz 屏上就是 165）。暂停时画布背板分辨率降到 0.7×，但这一项的收益小于本机测量噪声，只有机制可说、数值未获证实。
4. **安全模式的代价是真实的**：开启后只用明文 `http://` 接口的音源会解析失败（报错会写明是它拒的），新装音源默认禁用需要手动启用。这三个后果都写在开关旁边，不是隐藏行为。
4. **更新检查只提示**：拉取版本清单并打开下载页，不做静默安装。
5. **本地 HTTP API 默认关闭**：开启后只监听 127.0.0.1，除 `/api/health` 外都要 token。
6. **批量修改歌曲信息仅支持 MP3**（写入文件内的 ID3v2.3），对话框会先说明选中里有多少首是 MP3。
7. **曲库索引进 SQLite，收藏/历史/歌单仍以本机存储为准**，并保留 JSON 镜像双写，任一损坏都能恢复。
