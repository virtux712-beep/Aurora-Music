# Aurora Visual Engine —— 架构、审计与实现状态

> 这份文档同时是三件事：现有视觉系统的**审计**（优点 / 缺陷 / 瓶颈 / 可复用 / 需重构）、
> 新视觉引擎的**架构说明**，以及需求清单的**诚实实现状态**（做了什么、没做什么、为什么）。

## 一、审计：现在的 Aurora 视觉系统是什么

### 模块与职责

| 层 | 位置 | 职责 |
|---|---|---|
| 主题数据 | `src/shared/theme.ts` | `ThemeDefinition` = 颜色令牌 + `ThemeEffects`（粒子/密度/速度/漂移/辉光/音乐联动/背景配方/沉浸配方/歌词配方/脉冲配方） |
| 主题引擎 | `renderer/theme/skins.ts`、`theme/apply.ts`、`theme/palette.ts` | 六套内置皮肤的明暗双套调色板、`oklab` 混色、令牌写进 `:root`、用户主题加载 |
| 动画引擎 | `renderer/theme/effects/{background,ambient,player,lyrics}.ts` + `index.ts` | 每个「主题 × 档位」产出一份 `EffectPlan`（`data-*` 属性 + CSS 自定义属性），一次写入 |
| 粒子引擎 | `components/AmbientLayer.vue` + `effects/ambient.ts` | 五种粒子行为（星尘/落叶/晨雾/雨丝/胶片颗粒）共用一张画布与一个循环 |
| 音乐响应 | `effects/energy.ts` + `utils/spectrum.ts` | 分析器 → 一个能量值；订阅（画布层）与 `--music-energy`（样式层）两条通路 |
| 歌词渲染 | `shared/lyrics.ts`、`stores/lyrics.ts`、`components/lyrics/*`、`lyrics/scroll.ts` | 解析 + 时间索引（二分）、同步（只从 `currentTime` 派生）、渲染、滚动引擎 |
| 性能管理 | `visual/budget.ts`（纯策略）+ `visual/frame.ts`（运行时调速器） | 帧预算、刷新率识别、负载判定、降级/恢复、绘制门闸 |
| 渲染管理 | `App.vue` → `AmbientLayer` / `LyricsView` / `PlayerBar` | 一个外壳 + 页面级组件；无全局渲染器，各层自己持画布 |

### 优点（值得保留的）

1. **主题是数据，不是代码。** 用户主题走 JSON + 校验，永远不能执行代码；配方按名字选择、由引擎实现一次。
2. **效果应用是一次性的。** `planEffects` 把「主题 × 档位」压成一组属性/变量，之后每帧零成本——没有响应式重算。
3. **音乐联动的两条通路避免了重渲染。** 画布直接读订阅值，样式层读 `--music-energy`，都不进 Vue 的依赖图。
4. **档位是真的预算。** 发光/粒子乘数/像素比上限/是否跑重特效，而不是「开关一个 class」。
5. **歌词同步只从 `currentTime` 派生。** 拖动、暂停、切歌自动跟随，没有第二套时钟可以跑偏。
6. **失败隔离。** 视觉层崩了不牵连播放：分析器接入失败降级为「无联动」，画布异常被限制在自己的循环里。

### 缺陷（已经修掉的）

1. **性能看门狗挂错了地方，而且只朝一个方向走。** 它住在 `energy.ts` 里，靠 `subscribeSpectrum` 驱动——于是「主题不做音乐联动」的机器**根本没有看门狗**；它用固定 `22ms` 判定，在 165 Hz 屏上是 3.6 帧之遥（永远不触发），在 60 Hz 屏上却比现在严格；它只能降档，一次重负载会把效果永久拿走。
2. **帧预算不存在。** 没有任何「每秒最多画多少」的概念，装饰层各自按 rAF 全速跑。
3. **绘制层之间没有仲裁。** 粒子/频谱/唱盘各画各的，谁都不知道另一个在花同样的钱。
4. **显示刷新率从未被读取。** 高刷屏只体现在「rAF 更频繁」上。
5. **诊断不可见。** 没有任何地方能看到帧耗时、粒子数、档位依据——所以「卡不卡」只能靠感觉争论。
6. **同一份状态被算两次。** 帧耗时由 `energy.ts` 量、由设置页展示，而设置页自己又轮询一次；两个来源会漂移。

### 性能瓶颈（实测）

| 瓶颈 | 数据 | 处置 |
|---|---|---|
| 粒子画布的绘制次数 | 165 Hz 屏上无上限时 ~165 次/秒 | 门闸按图层限速（30 档实测 26.4 次/秒） |
| 频谱柱状图（最重的单帧绘制） | 与粒子同频竞争 | 同一个门闸 |
| 唱盘旋转 | 每帧一次样式写入 | 同一个门闸（角度按时间积分，跳帧不影响速度） |
| 歌词滚动 | 每帧一次 `scrollTop` 写入 | **不受门闸限制**：这是正在阅读的内容 |
| 帧耗时统计本身 | 每帧一次数组写入 | 环形窗口 180，决策 300 ms 一次 |

### 可复用（保留原样）

`shared/theme.ts` 的 `ThemeEffects` 形状、`theme/skins.ts` 的调色板生成、`theme/apply.ts` 的令牌写入与清理、`effects/*` 的四角色模块拆分、`utils/spectrum.ts` 的分析器接入、`lyrics/scroll.ts` 的滚动引擎、`shared/lyrics.ts` 的解析与索引。

### 需要重构（已重构）

`effects/energy.ts` 里的看门狗职责 → 拆到 `visual/`；`effects/levels.ts` 增加上行的 `upgrade(level, ceiling)`；设置页的帧耗时来源 → 改为调速器的单一来源。

## 二、Aurora Visual Engine 架构

```
visual/budget.ts      纯策略：预算 / 刷新率识别 / 负载分级 / 滞回 / 缓动曲线
visual/frame.ts       运行时：一个测量循环、绘制门闸（按图层）、负载看护、DOM 镜像
theme/easter.ts       纯规则：陪伴记录 / 连听计数 / 夜晚判定 / 静电概率与冷却
theme/recommend.ts    纯规则：标题·流派·封面色 → 主题推荐（带理由，会拒绍）
theme/skins.ts        主题数据（含明暗双套 + effects 配方）
theme/effects/*       每主题每档位一份 EffectPlan（属性 + 变量）
components/AmbientLayer.vue     粒子（唯一消费者语义：每层各自限速）
components/AuroraLab.vue        诊断叠加层（Ctrl+Shift+A）
```

**解耦边界**：`visual/` 不 import 任何 Vue / store / 组件；它只做四件事——测量、判定、放行、上报（`installGovernor` 把决策交给 store，DOM 镜像给脚本读）。
**崩溃隔离**：`visual/` 的每条测量路径都是全函数（不抛）；门闸只返回布尔；调速器不持有播放状态。视觉层任何一层挂了都影响不到播放——播放路径完全不经过这里。

## 五、已知取舍（写在代码注释里，也写在这里）

1. **负载线有 60 fps 地板。** 纯按屏幕刷新率判定会让 165 Hz 屏上的 60 fps 应用被判过载——第一轮打包验收就踩到了（档位掉了一级，四条无关的视觉检查一起变红）。
2. **只探测「紧窗口」才认刷新率。** 忙的时候帧间隔分布很宽，其中位数就是「这台机器刚才在干什么」；用它反推屏幕会把预算改宽，然后自证健康（已修）。
3. **滚动与文字填充不受帧率上限约束。** 上限约束的是装饰性绘制（粒子/频谱/唱盘）；正在读的东西始终跟手。
4. **门闸按图层独立。** 共用一份时间戳会变成「谁先跑谁吃预算」，其余图层永远饿死——唱片就是这么不转的。
5. **推荐不自动切换主题。** 「主题自己变了」属于失控感，不属于智能。
